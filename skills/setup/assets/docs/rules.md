# 작업 규칙 상세 (글쓰기 · 자기검증 · ADR감지 · 할일감지 · 커밋)

> CLAUDE.md에서 옮겨온 상세 규칙이다. CLAUDE.md에는 매 턴 상기용 트리거만 남겼다.
> 큰 글·제안·문서를 내보내기 전, 그리고 매 턴 자기평가 시 여기 기준으로 훑는다.

## 문서 볼트 경계 규칙 (파일 위치를 정할 때마다)

`{{DOCS_DIR}}/`는 사람과 에이전트가 프로젝트 맥락을 읽는 문서 볼트다. 새 파일의 위치를 제안하거나 만들기 전에 다음 기준으로 구분한다.

- **이 폴더에 둔다:** ADR, 위키 노트, 설계 문서, 조사 결과, 작업 일지, 할일 원장처럼 프로젝트를 설명하는 문서.
- **이 폴더에 두지 않는다:** 소스 코드, 테스트 코드, 빌드 산출물, 캐시, 비밀 설정, 데이터베이스, 애플리케이션이 실행 중 읽거나 쓰는 JSON·CSV 같은 제품 데이터.
- 제품 데이터는 별도 결정이 없다면 저장소 루트 아래 `data/`처럼 역할이 드러나는 경로를 제안한다. 예를 들어 개인 도서관 CLI의 `library.json`은 `{{DOCS_DIR}}/library.json`이 아니라 `data/library.json`에 둔다.
- 사용자가 제품 파일을 문서 볼트에 두라고 명시하면 이 경계와 충돌한다고 알리고 대체 경로를 먼저 제안한다. 프로젝트에서 예외를 확정하면 그 이유와 범위를 ADR로 남긴다.
- 반대 방향도 있다: 조사·분석 결과처럼 지식이 될 산출물을 `data/`나 코드 쪽에 두려 하면, 위키 노트가 맞는지 먼저 따진다.

## 작업 일지 기록 규칙 (매 사용자 턴)

- 사용자 프롬프트 훅이 이번 턴의 세션 ID와 턴 번호를 알려준다. 최종 답변 전에 그 값을 포함한 `worklog.mjs append` 명령을 실행한다.
- 물음에는 사용자가 요구한 핵심을, 결과에는 실제로 판단하거나 변경한 내용을 한 줄로 요약한다. 계획과 실제 결과를 혼동하지 않는다.
- 대안 중 하나를 골랐으면 `--why`로 고른 것, 버린 것과 이유, 핵심 수치를 한 줄로 남긴다. 컴팩션 요약과 한 줄 결과 모두 이유를 잘 잃기 때문이다. ADR로 남길 만큼 큰 결정이면 ADR에 쓰고 여기에는 ADR 이름만 적는다.
- 코드·문서·도구 결과에서 새로 알아낸 사실(원인, 제약, 동작 방식)은 `--found`로 한 줄 남긴다. 도구마다 따로 요약하지 않는다.
- 파일을 변경하지 않은 질의응답과 승인 대기 턴도 기록한다.
- 기록 명령이 성공하기 전에는 최종 답변을 보내지 않는다. 종료 훅의 누락 경고를 받으면 안내된 명령을 실행한 뒤 다시 종료한다.
- 종료 훅의 자동 복구 항목은 정상 기록을 대신하는 방식이 아니다. 자동 복구가 생기면 다음 턴에서 원인을 확인한다.
- 백그라운드 작업 완료 알림은 사용자 턴이 아니다. 훅이 턴으로 세지 않고 기록도 강제하지 않는다. 쉬는 동안 온 알림은 다음 사용자 턴 직전에 `(자동 알림)` 한 항목으로 묶여 기록되고, 사용자 턴 도중 온 알림은 그 턴의 기록에서 함께 요약한다. 알림을 받고 파일 변경·배포 같은 실질 작업을 했다면 토큰 없이 `worklog.mjs append`로 따로 남긴다.
- 작업 중에 보낸 추가 메시지와, 중단한 뒤 다시 보낸 메시지는 진행 중인 턴에 합쳐진다. 훅이 알려 준 마지막 명령으로 한 번만 기록한다.

## 글쓰기 지침 (모든 글에 적용 — 대화·설명·문서. 참조 문서는 3·4만 예외)

대화든 문서든 아래 네 가지를 지킨다. **답·문서를 내보내기 전에 이 네 가지로 한 번 훑는다.**

1. 중학생도 이해할 수준으로 쓴다.
2. 어려운 말은 풀어쓴다. 꼭 필요한 전문용어는 처음 나올 때 한 번 쉽게 풀이한다. 직역·영어 전사보다 자연스러운 우리말을 쓴다(예: 커서→책갈피, catch-up→따라잡기, 축약본→요약). **내가 지어낸 합성어를 만들지 않는다.** 개념에는 쉬운 우리말 이름을 붙이거나 그냥 풀어 쓴다.
3. 긴 문장은 짧게 끊되 내용은 그대로 둔다.
4. "A가 아니라 B다" 부정 대구법, 상투적 전환어("특히·결국·놀랍게도"), 억지로 몇 개씩 나열하기를 피한다.
5. **꺾쇠 표기는 반드시 백틱 안에 쓰거나 이스케이프한다.** 옵시디언은 백틱 밖의 `<무언가>`를 HTML 태그로 해석해 그 뒤 서식을 통째로 삼킨다. 플레이스홀더는 `` `<이름>` `` 처럼 백틱으로 감싸고, 산문에 부득이 맨몸으로 쓸 때는 `&lt;`·`&gt;`로 적는다. (이 규칙은 참조 문서를 포함한 모든 md에 적용된다 — 서식 문제이지 문체가 아니다.)

**예외 — 참조용 문서(결정 로그·스펙·backlog·worklog)에는 3·4를 적용하지 않는다.** 이런 문서는 표·번호 목록으로 훑어보라고 만든 것이다. **단, 1·2(쉬운 말·조어 금지)는 참조 문서에도 그대로 적용한다.** 글·문서 작성을 에이전트에 맡길 때도 이 지침을 프롬프트에 넣는다.

## 해결안 자기검증 규칙 (제안·평가 전 반드시)

해결책이나 아이디어를 내놓거나 평가하기 전에, 스스로 반박 질문을 던져 전제가 맞는지 확인한다. 통과 못 하면 제안하지 않거나 한계를 밝혀 제안한다.

- **사람 모으기(모집) 아이디어**: "이건 아직 우리 서비스를 안 쓰는 사람 눈에 닿는가?" 안 닿으면 모집이 아니라 유지·추천으로 분류한다.
- **남의 성공 방식을 빌릴 때**: 그 방식이 되는 전제를 한 줄로 적고, 우리 경우가 그 전제를 만족하는지 확인한다(겉모습만 보고 옮기지 않는다).
- **검증 안 한 아이디어**: 별점(★)·"비용 0"·"자기증식" 같은 단정적 평가를 붙이지 않는다. 붙이려면 "미검증"이라 표시한다.
- 에이전트에 맡길 때도 이 규칙을 프롬프트에 넣는다.

## ADR 감지 규칙 상세 (매 턴 자기평가 — 트리거는 CLAUDE.md)

매 턴 응답을 마치기 전, 이번 프롬프트+결과가 ADR로 남길 만한 결정을 담았는지 **조용히** 자기평가한다. 해당하면 응답 끝에 한 줄로 "이걸 ADR로 남길까요?"라고 묻는다. 해당 없으면 아무 말도 하지 않는다(평가했다는 언급조차 하지 않는다 — 그것도 노이즈).

**2게이트 — 둘 다 통과해야 질문한다:**
1. **결과성**: 되돌리기 어렵거나 제품/비즈니스 방향을 바꾸는가? (지엽적 디테일 아님)
2. **근거의 비자명성**: 미래 독자가 코드·커밋만 봐서는 "왜 이렇게 했는지" 알 수 없는가?

**보정:**
- 애매하면 침묵한다. 놓친 ADR은 소급 기록 가능하지만, 과잉 질문은 신뢰를 깎는다.
- 이전 결정의 번복은 무조건 통과(기록 시 이전 항목에 링크).
- **트리거 아님**: 일상 코드 수정, 디버깅, 탐색/조사, 테스트용 설정, 파라미터 튜닝, 단순 질의응답.

승인 시 `{{DOCS_DIR}}/decisions/`에 **새 파일**(`D-슬러그-YYMMDD-HHMMSS.md`, 예: `D-원장ID형식-260807-193512.md`)을 만들고 `README.md` 인덱스에 한 줄 넣는다. 슬러그가 앞에 와서 무슨 결정인지 먼저 읽히고, 일시가 붙어 병렬 세션 간 번호 충돌이 사라진다. 기존 순번 ID(`D1` 등)가 있으면 그대로 두고 앞으로 만드는 것부터 새 형식을 쓴다.

## 할일 감지 규칙 상세 (매 턴 자기평가 — 트리거는 CLAUDE.md)

매 턴 응답을 마치기 전, 이번 프롬프트+결과에서 **새 할일이 도출됐는지** 조용히 자기평가한다. 해당하면 `scripts/tasks.mjs`로 등록한다(손으로 `{{DOCS_DIR}}/tasks.md`를 고치지 않는다 — 자동 렌더 파일).

- **사람이 해야 할 일**(내가 못 하는 것 — 상담·등록·계정 만들기 등): 등록한 뒤 응답 끝에 한 줄로 알린다("할일에 등록해뒀습니다: …").
- **AI가 할 일**: 등록한다(매번 알릴 필요는 없음).
- 등록 속성: 담당(ai/human/both)·행동(next/planning/waiting/someday)·긴급(high/med/low)·출처(어디서 나왔나)·필요하면 메모. Planning은 `--due`.
- **Waiting의 범위**: 제3자(사람·업체)의 응답만이 아니라, **다른 할일의 완료, 외부 사건, 조건 충족을 기다리는 모든 할일**을 Waiting으로 등록한다. `--wait`에 기다리는 대상을 구체적으로 적는다 — 다른 할일이면 그 ID(예: "T003 완료 후"), 조건이면 트리거(예: "사용자 10명 도달 시").
- **조건부·트리거 작업은 두 원장에 함께 등록한다.** tasks에는 Waiting으로(`--wait`에 트리거), backlog.md에는 "트리거 → 무엇" 형태로 적되 **tasks ID(`T-슬러그-YYMMDD-HHMMSS`)를 함께 적어 서로 연결한다**. backlog는 새 단계를 시작할 때 트리거 중심으로 훑는 용도, tasks의 Waiting은 review가 주기적으로 조건 충족을 점검하는 용도다.
- **단, 사용자가 명시적으로 보류한 항목은 등록하지 않는다.** 보류 항목을 Waiting에 넣으면 review가 그것을 다시 꺼내게 되어 리마인드 금지와 충돌한다. 사용자의 재개 선언이 곧 등록 시점이다.
- 적절한 시점엔 `node scripts/tasks.mjs review`로 열린 할일을 훑고, 오래된 것·기한 지난 것을 물어본다. **Waiting 항목은 대기 조건이 충족됐는지도 확인**한다 — 충족됐으면 next로 옮기고, 짝이 되는 backlog 항목을 정리한다.
- **완료와 취소를 구분한다.** 결과를 얻었으면 `done <id>`, 이유가 사라져 하지 않기로 했으면 `drop <id> --reason "<이유>"`다. 의미 없어진 할일을 done으로 닫으면 완료 아카이브가 거짓이 된다(GTD의 휴지통). 취소분은 tasks-done.md의 별도 "취소 아카이브" 절에 이유와 함께 남는다. 되살릴 트리거가 실재하면 drop 대신 Waiting으로 전환하고 backlog에 짝을 적는다. 취소·삭제는 사용자 확인 후에만 한다.
- **review 때는 최근 worklog 항목도 대조한다** — "~하기로 했다", "며칠 뒤", "예정" 같은 말로만 하고 등록 안 된 미래 할일을 찾아 등록한다. **위키 노트의 "미해결" 절도 훑는다** — 지식 질문이 아니라 실행 과제·조건부 작업이 거기 적혀 있으면 원장으로 옮긴다(미해결 절은 review 보호를 못 받는 그림자 원장이 되기 쉽다).

**노이즈 게이트(등록 안 함)**: 이번 대화에서 이미 끝난 것, 사소한 것, 이미 등록된 것, 지엽적 디테일. 애매하면 등록하지 않는다(과잉 등록은 원장을 쓸모없게 만든다).

관리 파일: `{{DOCS_DIR}}/tasks.md`(GTD 원장) · `{{DOCS_DIR}}/tasks.json`(캐논, 스크립트 소유) · `{{DOCS_DIR}}/tasks-done.md`(완료 아카이브).

## 위키 감지 규칙 상세 (매 턴 자기평가 — 트리거는 CLAUDE.md)

매 턴 응답을 마치기 전, 이번 프롬프트+결과가 위키 노트로 남길 만한 지식을 담았는지 **조용히** 자기평가한다. 해당하면 응답 끝에 한 줄로 위키 노트를 제안한다(`scripts/wiki.mjs`로 만든다). 해당 없으면 아무 말도 하지 않는다(평가했다는 언급조차 하지 않는다).

**2게이트 — 둘 다 통과해야 제안한다:**
1. **품 드는 종합**: 다시 만들려면 시간이 드는 분석·비교·조사·정리의 결과인가? (한 번의 짧은 답으로 끝나는 것이 아님)
2. **프로젝트 재참조성**: 이 프로젝트의 다른 작업에서도 다시 찾아볼 지식인가?

**보정:**
- 애매하면 침묵한다. 놓친 위키 노트는 나중에 채울 수 있지만, 과잉 제안은 신뢰를 깎는다.
- **거친 포착 우선**: 발동하면 완벽하게 다듬은 노트가 아니라 초안(`status: draft`)이라도 먼저 남긴다. 다듬기는 나중 몫이다.
- **리치 지식은 챗에만 남기지 않는다**: 표·근거처럼 알맹이가 큰 내용은 그 자리에서 파일로 떨군다. worklog는 색인일 뿐 내용 저장소가 아니다.
- **review 통합**: 할일 review 같은 적절한 시점에 초안 노트를 훑어 재발한 주제를 정식 노트로 승격하고, 같은 대상을 설명하는 노트는 합친다.
- **트리거 아님**: 일상 코드 수정, 디버깅, 단순 질의응답, 이번 한 턴에서만 쓰이는 정보.

승인 시 `node scripts/wiki.mjs new "<제목>" --summary "..."`로 노트를 만들고 본문을 채운다(구조는 스크립트가, 본문은 어시스턴트가 채운다).

## 커밋 규칙

- 한국어 커밋 메시지, 명령형.
- 결정이 담긴 커밋에는 `Decision: <슬러그>` 트레일러를 붙인다(슬러그는 ADR 파일명의 슬러그 부분). `.githooks/commit-msg` 훅이 트레일러는 있는데 `{{DOCS_DIR}}/decisions/` 변경이 없으면 경고한다.
- 커밋 푸시는 사용자가 명시적으로 요청할 때만.

# 워크트리 병합 (worktree-merge)

여러 워크트리로 병렬 작업한 결과를 기본 브랜치(master/main)로 모을 때 쓴다. 이 하네스의 원장(worklog·tasks·ADR·wiki)은 공유 자원이라, 병렬 세션이 각자 쓰면 병합 때 충돌한다. 이 스킬은 그 충돌을 진단하고 안전하게 병합한다.

핵심 전제: **사용자는 git 병합을 직접 다루지 않는다고 가정한다.** 사용자에게는 "무엇이 들어오나 · 어디가 부딪히나 · 되돌릴 수 있나" 세 가지만 보여주고 **진행/중단만** 받는다. 나머지는 AI가 아래 절차대로 실행한다.

## 절차

### 1. 진단 (읽기 전용, 아무것도 바꾸지 않음)

사용자는 `/worktree-merge <워크트리 브랜치명>`으로 이 스킬을 부른다. 넘어온 인자 `$ARGUMENTS`가 병합할 브랜치명이다. 그 인자로 진단 스크립트를 실행한다:

```
node scripts/worktree-merge-inspect.mjs $ARGUMENTS
```

브랜치명 없이 `/worktree-merge`만 불렀다면 `git worktree list`·`git branch`로 병합 후보를 확인해 사용자에게 보여주고, 어떤 워크트리를 병합할지 먼저 정한 뒤 그 이름으로 위 스크립트를 실행한다. **여러 워크트리를 한꺼번에 병합하지 않는다 — 한 번에 하나씩, 각 병합은 직전 병합이 반영된 기본 브랜치 기준으로 진행한다.**

이 스크립트가 "표 + 위험도" 보고를 출력한다 — 들어오는 산출물 표, 충돌·해소 계획 표(항목별 🟢🟡🔴), 분기 유형, 되돌리기 가능 여부, 종합 위험, "진행할까요?". **출력을 그대로 사용자에게 보여준다. 요약하거나 바꾸지 않는다.**

### 2. 사용자 결정 대기

진행/중단만 받는다. 중단이면 아무것도 하지 않고 끝낸다.

### 3. 진행 시 — 분기 유형에 따라 병합

**fast-forward인 경우** (진단이 "fast-forward"라고 표시):
1. 기본 브랜치 작업 트리의 미커밋 원장 변경을 커밋하거나 `git restore`로 되돌린다(무엇을 되돌리는지 사용자에게 한 줄로 알린다).
2. `git merge --no-ff --no-edit <브랜치명>` — 병합 흔적을 남긴다.
3. 브랜치가 이미 기본 브랜치를 포함하므로 worklog 번호 충돌이 없다. 다음 worklog append에서 state가 자동 복구된다.

**병렬 분기인 경우** (진단이 "재번호 필요"라고 표시):
1. 미커밋 원장 변경을 커밋하거나 되돌린다.
2. **worklog 재번호**: 세 판본(공통 조상 `git merge-base`, 기본 브랜치 현재, 브랜치)을 비교한다. 공통부를 떼고, 두 꼬리를 **시간·도착 순으로 재배치**한 뒤 번호를 다시 매긴다.
   - **분기 전 항목은 번호 유지**, 분기 후 브랜치 항목은 offset만큼 뒤로 이동.
   - ⚠️ **요약 헤더의 앞 숫자와 뒤 숫자, 그리고 본문 속 `(#N)` 포인터를 함께 옮긴다.** 뒤 숫자를 빠뜨려 `[요약 #211~178]`처럼 시작>끝이 되는 게 단골 버그다.
   - `worklog-state.json`의 `next`는 손대지 않아도 된다(자동 복구가 다음 append에서 최대 번호+1로 맞춘다).
3. 재번호 통합본을 커밋한다.
4. `git merge -X ours --no-edit <브랜치명>` — worklog는 통합본을 우선한다. 산출물·새 파일은 브랜치판이 그대로 들어온다.

### 4. 검증

```
python3 - <<'EOF'
import re
m = open('{{DOCS_DIR}}/worklog.md').read()
nums = [int(x) for x in re.findall(r'(?m)^## \[#(\d+)\]', m)]
missing = [n for n in range(1, max(nums)+1) if n not in set(nums)]
dups = [n for n in set(nums) if nums.count(n) > 1]
print('범위', min(nums), '~', max(nums), '| 결번', missing or '없음', '| 중복', dups or '없음')
assert '<<<<<<<' not in m, '충돌 마커!'
print('충돌 마커 없음')
EOF
```

새 ID 형식(`D-슬러그-일시`, `T-슬러그-일시`) 덕분에 ADR·tasks는 병렬 발번해도 충돌하지 않는다. 만약 진단이 🔴(옛 순번 충돌)을 냈다면 그 파일명·참조만 수동 재번호한다.

### 5. 포인터 갱신

재번호로 바뀐 worklog 번호를 참조하는 파일을 고친다: tasks 항목의 출처(`worklog#N`), 위키 노트의 근거(`worklog.md #N`), backlog 등. **단 worklog 항목 본문 속 "당시 상황" 서술은 역사 기록이라 그대로 둔다.**

### 6. 뒷정리

- 워크트리 관리 도구를 쓰면(예: Orca) 카드를 완료 상태로 바꾼다. 그 도구가 워크트리 삭제를 담당하면 삭제는 사용자에게 맡긴다.
- 순수 git이면 병합 확인 후 `git worktree remove <경로>`·`git branch -d <브랜치명>`로 정리하되, 삭제 전 브랜치 HEAD가 병합 커밋으로 기본 브랜치에 도달 가능한지(`git branch --contains <sha>`) 확인해 작업물 유실이 없음을 보고한다.
- worklog에 병합 턴을 기록한다.

## 위험도 읽는 법

- **🟢** 자동 해소 — 재번호, state 자동 복구, 새 파일 진입. 대부분 이 등급.
- **🟡** 텍스트 충돌 가능 — 기존 문서를 양쪽이 수정했을 때. 병합 후 `<<<<<<<` 마커를 확인해 손으로 합친다.
- **🔴** 수동 개입 — 옛 순번 ID 충돌 등. 새 형식 도입 이후로는 거의 나오지 않는다.

## 하지 말 것

- 사용자에게 git 명령·프로토콜을 설명하지 않는다(사용자는 병합을 직접 다루지 않는다고 가정).
- 진단 보고를 요약하지 않는다(표+위험도를 그대로 보여준다).
- 워크트리를 임의로 삭제하지 않는다.
